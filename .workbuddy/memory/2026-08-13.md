## 修复两个 Bug（ns-sql-editor）

用户报 3 个 Bug，其中 Bug3（切换连接重连）用户自述看错了，先不管。

### Bug1：跨服务对比，主会话清单为空时无法从目标同步
- 根因（两层）：
  1. UI 层：`LinkageCore.maybeCompare()` 旧守卫 `if (mainItems.length === 0 || ...)` 把「主会话空 + 目标有数据」整段跳过 → 同步按钮不出现（已改：仅 `if (targetItems.length === 0)` 跳过）。
  2. **真正的失败点**：`syncStatement` 的 INSERT 只填 `DSNAME/DBQUERY/SORTBYCONTENT/REF1`，不填页面级「基础资料」`TABNAME`。空清单时无已有行可继承 `TABNAME`，服务端拒绝 INSERT —— 与 Bug2 同根因。仅改 UI 守卫无法让同步真正成功。
- 修复（与 Bug2 对称）：`syncStatement` 增加可选 `extraFields?: StatementFields` 并展开进 `buildInsertModel`；`LinkageCore.handleSync` 从选中页面菜单节点取 `cname||ename` 作为 `TABNAME` 透传（`LinkageCore.vue` 新增 `mainPageMenuName` computed）。
- 验证：`npm run build` 通过（vue-tsc 类型检查 0 错；仅 @vueuse/core / chunk-size 第三方告警）。

### Bug2：空语句清单时新增语句失败（依赖服务端基础资料）
- 根因：新增首条语句依赖页面级「基础资料」（`TABNAME` 等），空表时无已有行可继承，服务端拒绝。
- 修复：`createStatement` 增加可选 `extraFields?: StatementFields`；`NewStatementDialog` 把选中菜单的 `cname/ename` 作为 `TABNAME` 透传填补。
- 假设字段为 `TABNAME`（菜单名映射页面名）。若服务端实际要求 `TABTY` 等其它基础字段，需用户确认后补。
- 验证：类型检查通过。

## 备注
- `@nameson/sqlutils` 的 `generateDataModel` 是纯客户端建模（自动填 ADDUSER/UPDDTTM 等元数据），不依赖服务端；Bug2 的服务端依赖在 PRJOBJDS 页面级字段。
- Vite 构建的 `prepare-out-dir` 的 safe-delete trash 钩子偶发失败（删旧 dist 报错），属环境问题，清掉 dist 后重 build 即正常。

## 二次修正：同步进空主清单时不再查主库取序号（Bug1 续）
- 用户反馈：主清单为空、从别的库同步时，`syncStatement` 仍用 `getMaxTabseq(mainServerUrl, mainObjectId)` 逐条查主库取序号——空表结果恒为 1，无意义往返。
- 原则（用户明确）：基础资料/序号应从自身页面来，空清单同步不该再读主库；写主库（saveData INSERT）是必须的，但"查"主库无意义。
- 修复：
  - `api/linkage.ts`：`syncStatement` 去掉 `getMaxTabseq` 主库查询，改由调用方传入 `nextSeq`；并移除对 `getMaxTabseq` 的 import。
  - `LinkageCore.vue`：`handleSync` 从已加载的 `linkage.mainStatements` 本地推算起始序号（空→1，非空→max+1），按批次自增后逐条传给 `syncStatement`。
- 效果：同步过程零主库读请求，仅最后 saveData 写入。TABNAME 仍由 `mainPageMenuName`（自身菜单节点）提供。
- 验证：`npm run build` 通过（vue-tsc 0 错；仅第三方告警）。
